# 上游交接契约

上游源 skill 按本书大纲生成项目配套材料；下游源 skill 验收并消费。以下是项目交接要求，不是要求源 skill 安装目录自带每本书的表单。材料可以合并文件，只要条目、来源和实际路径可查。

## 先区分批次开写与已有文本任务

- 新写、续写或将正文纳入正式批次实绩，执行下文完整交接、active 包与阶段验收要求。
- 用户仅要求润色或审查已给定的片段/章节/全书时，建立本次范围记录：任务类型、文本路径/版本、用户给定或已有的情节/POV/风格约束、所需上下文、允许修改边界和输出位置。记录可内嵌报告，不强造项目配置、历史 writer 报告或 active 包；已有相关项目材料仍需核对，consumed 包可作历史依据，不能作为新写凭据。
- 该分支只证明所请求范围的润色或审查。缺关键证据时列未能验证项，暂停依赖它的修改或结论，不猜造前史；要求大纲对应审查却未提供大纲时仍需补证。
- 仅交相应文本与真实角色报告，不补造四阶段记录，不更新正式状态、规划或下一包。主 agent 可验收本次限定交付；以后要接受为正式批次实绩，须补齐当时适用的完整验收门。

下文开工包及四阶段要求适用于第一种任务；已有文本任务按本节限定范围执行。

## 按本书验收材料

| 类别 | 材料及用途 | 验收方式 |
|------|------------|----------|
| 通用必需 | 本书配置、当前入口、已审卷/段纲与本批章纲、技法与可写材料、初始事实或已接受正文基线、风格依据、进度与当前执行包 | 不强制分卷；确认书、范围、版本、硬约束、可设计空间、待定项和来源。技法与可写材料须足够支撑本批，通常每章 1–3 个落点，不机械凑数。未知风格可记录未定或本轮提案，不冒称用户已定 |
| 内容需要 | 人物/关系、术语认知、角色认知路径、关键道具、伏笔及回收窗口、专项技法 | 本批依赖的硬事实必须可核；不涉及者注明 `N/A` 和理由，可在配置/包中内嵌，不强制另建表或专门体系 |
| 阶段需要 | 上批终审、卷级接口、卷末/跨卷报告、迁移接管记录 | 首批无需虚构上批报告；单卷或未到交接阶段可 `N/A`；卷末/跨卷或已知偏离触发相应审查 |

规划重要条目应可区分“大纲已定 / 本轮设计 / 待定 / 已接受正文实绩”。待定项若影响本批硬连续事实，不得以 `N/A` 掩盖。

## 输入包和当前执行包

本批输入包保存规划依据与来源条目；当前执行包是主 agent 按最新已接受事实校准的执行快照，不是独立事实来源。两者可合为一个 Markdown 文件的不同区块。

输入包与执行包共用以下元数据；合并文件时区分两种职责，输入包不另成为正文开写入口：

- 本书标识；包 ID、版本与类型（输入/执行或合并）；章节范围。
- 规划来源路径、条目及版本；事实基线路径与版本（零正文注明初始状态版本与“无已接受正文”）；风格依据路径与版本。
- 状态：`draft` / `active` / `consumed` / `invalidated`。
- 生成者；验收者、验收结论和证据路径/定位。

版本可用修订号或哈希，无须新建 JSON 系统。正文内容至少包括当前事实、批次目标、执行模式、分章施工卡、硬点与对应章纲来源条目、软目标、回读触发器和写后覆盖表。验收需核对硬点是否完整承接章纲，不能仅因元数据齐全就放行。

## 生成、验收与状态

1. **零正文首批**：主 agent 依据已审规划、初始事实和风格配置生成 `draft`，核对范围、来源和硬点后改为 `active`。无需上一批终审证据。
2. **已有正文接管**：定向提取已写且确认有效正文的人物、关系、道具、术语、认知、伏笔和风险实绩，保留通过章节；旧规划冲突按 A/B/C/D 裁决。未审草稿另列候选，不能混入基线。
3. **后续批次**：上一批修复复审、主终审及必要跨卷审查完成，接受实绩入账并更新后续规划后，才生成、验收新包。
4. 当前入口只指向本书一个可执行的 `active` 包，不可同时保留两个“当前版本”。`draft` 未验收、`consumed` 已消费、`invalidated` 已失效，均不可作为新批开工依据。
5. 批次终审及实绩入账完成后，旧包标为 `consumed` 并保留报告引用；依赖规划、事实基线或风格约束改变时，相关未消费包标为 `invalidated`、移出入口，重建或修订验收后才能激活。

激活新包前必须核对当前入口、项目进度/逐章恢复记录和接受事实基线：已接受范围、当前批次、包 ID/版本与下一动作应互相一致。可以合在一个文件；分散保存时须一起同步并回读，不能只更新状态文件或运行日志、让总进度仍把已接受章列为待写。发现这类不一致先修正记录并重验入口，禁止带着矛盾进度开下一批；结束时同样核对，不靠一份完成报告覆盖仍指向旧 active 的入口。

content-writer、polisher、outline-checker 只提出变化候选，不生成、修订或登记下一批执行包。若主 agent 本地兼任这些角色，仍须在完成终审裁决后切换主编职责处理执行包。

## 缺失时的处理

- 缺本批章纲或卷级硬目标：反馈上游补足对应材料，不重做全书规划。
- 缺 active 包：按首批、接管或后续批次对应入口初始化/重验，不让 writer 越过验收开写。
- 缺伤势、资源、知情、道具转移、伏笔窗口等本批硬连续事实：定向回读已接受正文、状态来源和报告；仍不能确认，列缺项、所需证据与受影响章节，暂停依赖该事实的正文并反馈上游/用户。不得只标“风险”后凭猜测继续。
- 表单名称不同或可合并：核对实际内容，不要求机械复制目录；确实不适用才写 `N/A`。
- 缺技法：按 [wiki-routing.md](wiki-routing.md) 定向补技法，保持已审章纲边界。
- 缺报告：首批按阶段处理；已有批次缺必需终审或当前修订对应报告，补审后才能接受实绩或放行下一批。

交接验收要记录通过项、缺项/不适用理由、版本依据及可执行范围；仅写“材料齐全”不构成验收证据。
